## Superseded: promo dates

#336's `daysUntil` counted inclusive **machine-local** calendar days and returned `1` on the last day. #501's shared helper:

- interprets stored `YYYY-MM-DD` as America/Toronto
- is live through `promoEndOfDay` (next Toronto midnight minus 1ms)
- returns `0` on the last Ontario day (`formatExpiry` → "Expires today")
- uses IANA offset resolution so EST/EDT both work
- is the same function object on the client (`quote-utils` / `finance` re-export) and on the edge

Direct check on this HEAD:

```
daysUntil('2026-08-31', 2026-08-31T16:00:00.000Z) === 0   // noon EDT, last day
daysUntil('not-a-date') === NaN
daysUntil('2026-13-40') === NaN
```

#336's `finance.promoDate.test.ts` expects `1` on that last day, so it is not a valid regression test against current main. The DST case it added is already covered more tightly (EDT and EST, 9am / 11:59pm / 12:01am) in `quote-utils.promoDate.test.ts`.

`parsePromoCalendarDate` still accepts `2026-02-30` (day `<= 31`) and `daysUntil` then treats the UTC-normalized March 2 as a past date (`0`), not `NaN`. That is not the countdown/DST bug #336 was fixing, and inventing a calendar-validity check here would be new work.
